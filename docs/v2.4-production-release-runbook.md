receipt verification proved that Janitorial QA receipt `26-009` was

The incident was recovered, but the operation was **not a successful
non-disruptive isolated restore rehearsal**. The existing snapshot also
PREDATES the new Janitorial QA receipt and potentially later transactions.
The word `main` in Neon currently names the snapshot copy, NOT the
live Production branch. Use exact branch IDs, never display names alone.

**Required before any Production DDL:**
- Obtain separate owner authorization for a fresh **post-incident
  pre-release** Production snapshot from original branch ID
  `br-calm-dew-b3vd1ira`. Verify and record snapshot ID, source ID,
  timestamp, and successful completion.
- Rehearse **only a safe isolated recovery**. Have a second operator review
  the documented Neon restore method and explicitly set
  `finalize: false` for a branch-only snapshot rehearsal if supported.
  **Never omit `finalize` in a Production snapshot restore request.**
  Check Vercel bindings, source/destination branch IDs and compute endpoints
  before and after, and do not initiate a restore if the procedure cannot
  guarantee isolation. Escalate to Neon support if uncertain.
- Confirm a rollback operator, acceptable recovery-point/time objectives,
  Vercel's previous deployment and PITR/snapshot retention. An empty
  scheduled snapshot list does not prove or disprove PITR availability.
- Arrange a maintenance/write-freeze window and refresh all Production
  receipt, fund and audit balances immediately beforehand.
- Never reveal passwords or personally identifying financial records in
  the PR, release logs, or screenshots.

**STOP if** a backup is too old, its restore has not been safely rehearsed,
the intended original branch/endpoint differs, or the recovery plan risks
discarding transactions made since snapshot creation.

## 6. Failure handling and data preservation

| Failure point | Safest immediate response |
| --- | --- |
| Backup or target mismatch | **Stop.** Do not begin Production schema changes. |
| Migration fails or leaves unresolved Prisma history | Keep maintenance freeze; collect sanitized migration output and the failed migration name, verify DB state, decide on a **reviewed forward-fix**. Do not `resolve --applied` blindly or edit historical migration files. |
| DB migrations succeed, Vercel deploy fails | Keep the previous Production application serving if compatible. Leave additive columns/tables/sequence in place; do not drop them to force a rollback. Investigate before retry. |
| New app deploys but fails | Stop writes; roll back **application deployment** to a verified previous commit/deployment if compatible. Preserve receipt/PaymentRequest/audit records; avoid destructive DB rollback. |
| Database integrity issue after genuine financial writes | Escalate; reconcile and preserve all receipts/outbox/audit records posted since the recovery point. A snapshot restore to Production can erase legitimate intervening transactions—**never execute without separate approval, outage plan, and recovery reconciliation**. |

A Postgres sequence can advance during an aborted transaction. Gaps in OR numbers are expected. Never restart or reuse issued numbers.
