1. Verify the SHA and direct Production host again immediately before migration.
2. Apply **Prisma migrate deploy** to Production *before* the v2.4 application is deployed. Migrations are additive; previous application should remain compatible.

4. Check sequence/table/index existence, the six earlier migration records, calendar timestamp types, and representative transaction counts/fund totals. Check for schema drift against the reviewed Prisma model on a disposable copy as well.
5. Only after the DB gate passes and the owner separately authorizes application rollout: merge PR #35 or use an approved commit-specific deployment procedure. Note that merging into `main` may trigger **automatic Vercel Production deployment**.
6. Confirm the deployed code SHA, auth/tenant access and receipt behavior in Production. Use **read-only** smoke checks first. Any real posting needs a separate business-approved controlled test; do not silently issue genuine payment receipts.
7. Resume financial writes only after final release verification and explicit operator signoff; monitor errors, receipt collisions, audit logs, remittance verification, fund totals and digital receipt outbox. Record incident contact and maintenance timestamps.

Prohibited commands on Production: `prisma db push`, `prisma migrate dev`, `prisma migrate reset`, direct `DROP`/table recreation, receipt sequence restart or reuse, unchecked automated retries.

## 6. Failure handling and data preservation

| Failure point | Safest immediate response |
| --- | --- |
| Backup or target mismatch | **Stop.** Do not begin Production schema changes. |
| Migration fails or leaves unresolved Prisma history | Keep maintenance freeze; collect sanitized migration output and the failed migration name, verify DB state, decide on a **reviewed forward-fix**. Do not `resolve --applied` blindly or edit historical migration files. |
| DB migrations succeed, Vercel deploy fails | Keep the previous Production application serving if compatible. Leave additive columns/tables/sequence in place; do not drop them to force a rollback. Investigate before retry. |
| New app deploys but fails | Stop writes; roll back **application deployment** to a verified previous commit/deployment if compatible. Preserve receipt/PaymentRequest/audit records; avoid destructive DB rollback. |
| Database integrity issue after genuine financial writes | Escalate; reconcile and preserve all receipts/outbox/audit records posted since the recovery point. A snapshot restore to Production can erase legitimate intervening transactions—**never execute without separate approval, outage plan, and recovery reconciliation**. |

A Postgres sequence can advance during an aborted transaction. Gaps in OR numbers are expected. Never restart or reuse issued numbers.
