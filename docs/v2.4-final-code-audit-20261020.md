### Why the financial fixes matter

Configured funds are authoritative. Historical ledger buckets are a calculated view, and the existing schema does not enforce a foreign key from `Collection.fundAllocation` to `Fund.fundName`. The new server checks cover **cashier and online-remittance receipt issuance**, not every historical financial action in the application.

A student collectible uses a compound identity of **tenant, academic period, student, item and category**. Previously, public online submissions stored a generic `Online Remittance` category even when the officer verified a real `Membership Fee`. That can create a valid receipt while failing to reduce a matching collectible assessment. New transactions now use the configured category when resolvable; **historical already-posted remittances are not silently rewritten**. If older balances disagree, perform an approved, audited one-off reconciliation.

For package payments, the authorized individual `CollectionSetup.targetFund` values still determine final allocations. Selecting a fund in the officer dialog does not override a configured assessment. Duplicate fee descriptions across different categories must be resolved at Fee Setup rather than guessing the wrong accounting category.

### Security, tenant isolation and concurrency

- Cashier and remittance action guards use server-side `requireTabAccess(tab, department)`, and the access guard loads an active organization and tenant membership from the database. Global Super Admin privilege requires a verified global-admin session, not merely client-supplied role text.
- Cashier write/retry paths use tenant-scoped payment request UUID + payload fingerprint, a `PaymentRequest` unique constraint, serialized transactions, and database-owned receipt allocation. Successful replay returns the existing valid receipt; a changed payload or invalid/VOID receipt fails.
- Online approval uses an organization-scoped remittance lookup plus conditional status update and creates its verified Collection/receipt/audit entry atomically.
- VOID includes tenant/period constraints, all package split lines, reversal of linked online remittance and student collectible/penalty balances, and ledger solvency checks. Unsupported legacy/mixed obligations fail closed for manual review.
- The database uses integer-cent calculation checks at the financial interfaces, but several historical Prisma monetary fields are still `Float`. Conversion to `Decimal` is a separate planned migration and is **not represented as solved** by this PR.

**Test limits:** The new integration suite sends authenticated HTTP requests to a **CI-only adapter calling the real action functions**. It is not a full browser-native Next.js Server Action transport/OTP/login test, nor a complete performance/load test for every tenant or combination of cashier, remittance, rollover and VOID. The public submission's `X-Forwarded-For` rate limit relies on a documented trusted ingress configuration; validate that trust boundary separately.

### Additional findings and verified fixes

- **FIN-07 — HIGH, fixed:** Direct invocation of the cashier Server Action could invent an unconfigured fee, client rate and category and issue a receipt to an existing fund. The server now requires **exactly one configured** `CollectionSetup` matching tenant/AY/term/category/name and takes its authoritative amount and target fund. Authenticated integration rejects a forged ₱25,000 fee and creates neither Collection nor PaymentRequest.
- **FIN-08 — HIGH, fail-closed guard:** Legacy cashier credits aggregate by normalized item description. Duplicate item descriptions across categories, duplicate setups within one category, or conflicting-category historical receipts can misstate dues. Cashier now refuses ambiguous setups or receipt histories; the online package verifier rejects duplicate package item names. Existing records are **not rewritten**. Authorized fee renaming or audited historical reconciliation is required before posting affected items.
- **SEC-01 — authorization tested:** A signed JWT claiming Administrator while its current `TenantUser` record is Viewer with only overview permission was rejected by **both** cashier and remittance server actions. Role and module checks are sourced from current tenant membership rather than trusting a JWT's role text.
- **UX-01 — corrected:** All configured fund destinations remain visible for remittance approval, even if a fund's net ledger balance is negative. Income can replenish such funds.
- **CI-01 — corrected:** A TypeScript projection for the new historical-category guard and a test assertion initially failed. Both were fixed; the final commit passed all five workflows (including authenticated concurrency integration) and Vercel Preview.

### Business-policy and residual risks — owner must decide before Production release

1. **Ad hoc online remittances:** The verified online-remittance action currently accepts an item description with **no matching configured fee** and lets an authorized reviewer post it to a configured fund at a derived rate. Cashier is now stricter. The owner must decide whether ad hoc/donation-type online collections are intentional and require separate auditable permissions, or whether **every** online payment must match Fee Setup. Do not silently change this behavior for pending proofs.
2. **Package scope:** Cashier allocates the department's package items within the chosen category; online remittance with a `Departmental Fee Package` description currently selects **all** period package items across categories. Determine whether this is intended institution-wide package collection or a category-specific obligation. Reject or redesign ambiguous proofs before relying on it.
3. **Historical generic categories:** Existing `Online Remittance` category receipts are not migrated/reclassified; mismatched historical balances must be audited individually, never silently rewritten.
4. **User role policy:** The existing user-management UI and server intentionally interpret an *empty* allowedTabs selection as the role's **default** scope; Inactive/Blocked status revokes full login access. This was confirmed in source and not changed.
5. **Public ingress trust:** The proof-submission throttle's `X-Forwarded-For` derivation assumes a trusted Vercel reverse-proxy configuration. Validate deployment routing and header trust separately.
6. **QA tenant segregation:** Janitorial is a logical sandbox **inside** Production; exclude its data from consolidated real institutional financial reports wherever those totals are computed.
