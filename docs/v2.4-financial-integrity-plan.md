# CLEAR v2.4 — Financial Transaction Integrity (PR A)

Status: design and review checklist; no production transaction behavior changed by this document.

## Scope
- Preserve current payment, package-split, penalty, remittance, collectible, fund, and void workflows.
- Standardize serializable Prisma transaction retries (P2034) where appropriate; never retry irreversible external side effects.
- Design server-validated idempotency for payment and remittance operations. One key must map to one tenant, operation and immutable payload fingerprint. Return prior result on exact retry; reject reused key with changed payload.
- Keep multi-row official receipt groups working; do not add a naive unique(organizationId, orNumber).
- Keep all audit and balance mutations within the same database transaction.
- Keep Float-to-Decimal migration out of PR A.

## Acceptance tests
1. Simultaneous same-OR posts: one logical receipt group only.
2. Repeated identical request after timeout: no second charge, return original outcome.
3. Same idempotency key with different payload: reject.
4. Simultaneous penalty payments: no overpayment or lost updates.
5. Mid-transaction failure: receipt, ledger and audit effects roll back.
6. Two concurrent void requests: only one reversal.
7. Cross-tenant and unauthorized writes: denied.
8. Package split receipts and previous-term arrears: unchanged.
9. Closed period rejects writes.
10. External receipt dispatch only after commit, deduplicated.

## Implementation checkpoint — October 2026

- Shared `withFinancialTransaction` helper now retries Prisma `P2034` conflicts under PostgreSQL Serializable isolation.
- Collections, remittance verification/rejection, and void operations use the shared helper.
- Collections and online remittance verification acquire a transaction-scoped advisory lock on (organization, OR) before their final OR collision check. PostgreSQL automatically releases the lock on transaction completion.
- The existing `@@unique([organizationId, orNumber, itemDescription])` constraint is preserved because package payments may have multiple rows; **do not** replace it with `@@unique([organizationId, orNumber])`.
- Current implementation is **not yet verified**: a real PostgreSQL integration test must prove two concurrent postings of the same OR result in exactly one committed receipt group and no orphan penalty/collectible changes.
- Retry-after-success currently rejects an already-used OR; returning the prior success result requires a separate request-id idempotency mechanism. Do not claim full idempotent replay yet.
- Audit other OR-producing entry points and package-line suffix collisions before declaring the guarantee system-wide.
- Required gates: `npx prisma validate`, `npx tsc --noEmit`, `npm run lint`, `npm run build`, concurrency and rollback integration tests on an isolated PostgreSQL database. No production data should be used for testing.

## Automatic OR numbering update — October 20, 2026

- New receipts in Collections and verified Online Remittances are assigned by `allocateOfficialReceiptNumber` inside the posting transaction. The client no longer selects an OR number.
- The PostgreSQL `clear_receipt_sequence` migration must be applied before deploying the application changes. Existing Collection and OnlineRemittance OR values are not rewritten.
- New ORs use a UTC timestamp and a global non-cycling database sequence. Sequence gaps after failed transactions are expected.
- Package splits retain `-P02`, `-P03`, etc., and existing historical receipt formatting is preserved.
- GitHub CI currently tests sequence uniqueness, rollback behavior, parallel sequence allocation, TypeScript, financial source assertions, and the full Next.js production build.
- These checks do **not** establish application-level request idempotency, simultaneous posting correctness, or full rollback of linked fund/penalty/collectible records. Those still require staging integration tests.
- The earlier note about manual OR advisory locking applies only to the original implementation. The allocator now obtains the sequence value itself, then performs a collision check.
- Release order: verify backup; apply the sequence migration in staging; test concurrent approvals and failures; apply production migration in a controlled window; deploy the application after migration. Do not merge/deploy without owner approval.
